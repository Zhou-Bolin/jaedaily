任务 第一则

长上下文块复用

▶ YouTube ▶ B站↗ 原始论文
任务 93/100

你负责一个企业级长上下文 RAG 推理服务：每个请求由若干“证据块”拼接成 prompt，每个证据块在被拼接后会产生上下文化 KV cache。系统发现不同请求之间会复用相同证据块，但由于块前面的上下文不同，KV cache 只有在“前缀签名一致”时才能安全复用；同时 GPU cache 容量有限，预填延迟是主要瓶颈。给定一批离线日志：每个请求包含有序块序列、块 token 长度、请求到达时间、答案质量收益估计；线上要求 P95 首 token 延迟不超过 L，GPU KV cache 容量为 M tokens，且不能因为复用错误导致答案质量下降超过 ε。 请设计一个“证据块 KV 复用与驱逐”方法：包括如何定义可复用单元、如何决定哪些块值得缓存、如何在容量约束下驱逐、如何保证线上延迟和质量约束。请说明你的目标函数、核心方法、复杂度、边界条件，以及你会如何用离线日志评估再上线。

参考回答

我会先把任务建模成“带正确性约束的上下文化块缓存优化”，而不是简单按 block_id 缓存。一个缓存条目的 key 至少包含：模型版本、tokenizer 版本、采样/系统 prompt 相关配置、块内容 hash、块在 prompt 中的前缀签名 prefix_signature。prefix_signature 可以是前面若干稳定块的 Merkle hash 或完整 prefix hash；只有 key 完全一致时才允许直接复用该块 KV。对于不能完全一致但语义相近的情况，不能直接复用 KV，只能作为检索或重排特征，否则会引入隐性质量风险。

目标函数可以写成：最大化一段时间窗口内的预填计算节省减去缓存占用成本，并满足延迟和质量约束。对请求 r，若块 i 命中可复用 KV，可节省约 c_i = α * len_i * effective_attention_cost(prefix_i) 的预填时间；缓存成本是 len_i * hidden_layers * kv_bytes。质量约束通过规则保证：精确 key 命中质量损失近似为 0；任何近似复用都默认禁止，或只在 A/B 验证证明质量损失小于 ε 后开放灰度。

离线阶段，我会从日志构造候选缓存条目 e=(key, size, value, time_sequence)。value 不是简单频次，而是未来窗口内可带来的 latency saving，可按请求权重、P95 风险、SLA 等加权： value(e)=Σ hit_occurrence saved_prefill_ms * request_priority。 如果只做静态容量选择，可以近似成 0/1 knapsack：在容量 M 下选 value/size 高的条目；但线上访问有时间性，所以更实际的是“准入 + 驱逐”两层策略。

准入策略：当一个块 KV 计算完成后，估计它的 expected_gain = reuse_prob(key, horizon) * saved_ms。reuse_prob 可以由离线统计、时间衰减计数、租户/知识库/查询类型特征模型预测。只有 expected_gain / size 超过阈值，且不会挤出明显更高价值条目时才缓存，避免一次性长尾块污染缓存。

驱逐策略：用 GreedyDual-Size/Frequency 风格更合适，而不是纯 LRU。为每个条目维护 priority： score = H + expected_future_saving / size， 其中 H 是全局老化因子，被驱逐条目的 score 会更新 H，保证旧热点会自然衰减；expected_future_saving 可由近期命中频次、离线先验和请求优先级共同估计。容量不足时反复驱逐 score 最小的条目，直到能放入新条目。这样比 LRU 更能处理“长 KV、大块、低频”和“小块、高复用”之间的权衡。

在线路径上，请求到来后按有序块序列逐块计算 key。若 key 命中且缓存完整，就直接拼接对应 KV；若中间某块 miss，后续块的 prefix_signature 通常会变化，所以不能盲目复用后续块。工程上可以把 prompt 切成若干稳定段，比如 system prompt、租户固定文档、检索证据块；对稳定前缀做层级 prefix cache，减少“中间 miss 导致后续全 miss”的损失。对长请求可做 admission control：如果预计全量预填会超过 L，则优先保留能降低 P95 的高收益前缀块，必要时降级为减少证据块数量、启用小模型摘要或排队。

复杂度方面，设单请求有 k 个块，查找 key 是 O(k) 次哈希查询；每次准入或驱逐若用最小堆维护 score，是 O(log N)，N 是缓存条目数。离线统计若日志总块出现次数为 T，则构建候选和未来收益估计是 O(T) 到 O(T log T)，取决于是否按时间窗口排序。内存成本主要是实际 KV cache，元数据是 O(N)。

边界条件包括：模型升级、tokenizer 变更、系统 prompt 变更必须整体失效；不同 batch 中 position encoding、RoPE scaling、attention mask 必须一致；多租户数据不能跨租户复用，除非权限完全一致；流式生成时要区分 prefill KV 和 decode KV；GPU 间迁移要考虑 PCIe/NVLink 拷贝成本，若拷贝成本大于重算成本则不复用；缓存条目要有 TTL，防止知识库更新后使用过期证据。

离线评估分三步：第一，用日志回放评估 hit rate、saved_prefill_ms、P50/P95 首 token 延迟、缓存周转率和容量敏感性；第二，用 shadow traffic 验证 key 一致性、KV 拼接正确性、显存碎片和多 GPU 调度；第三，小流量 A/B，监控延迟收益、错误率、答案一致性、引用证据正确率和业务指标。若质量指标接近 ε，要回滚到只允许严格前缀命中的保守策略。

回答分析

强候选人应该先指出 KV cache 复用的核心难点是“上下文化正确性”，不能把相同 evidence block 当成天然可复用；其次要能把任务建模为容量约束下的收益最大化，明确 saved latency、cache size、reuse probability 和质量约束；再进一步给出在线可实现的准入、驱逐、失效和评估方案。好的回答会讨论为什么 LRU 不够、为什么 prefix signature 必须包含模型和上下文信息、为什么中间 miss 会影响后续块复用，以及如何处理多租户、模型升级、RoPE/position、GPU 拷贝成本等工程风险。常见错误包括：只按文档 ID 缓存 KV、忽略位置编码和 attention mask、把语义相似块拿来直接复用、只追求 hit rate 不看 saved_ms/size、不考虑缓存污染和显存碎片。出练习者可继续追问候选人如何证明质量不下降、如何在多 GPU 上放置缓存、如何在动态检索结果下提高 prefix 稳定性。

到达终点数字

▶ YouTube ▶ B站↗ LeetCode
任务 95/100

在一根无限长的数轴上，你站在`0`的位置。终点在`target`的位置。

你可以做一些数量的移动 `numMoves` :

  • 每次你可以选择向左或向右移动。
  • 第 `i` 次移动（从  `i == 1` 开始，到 `i == numMoves` ），在选择的方向上走 `i` 步。

给定整数 `target` ，返回 到达目标所需的 最小 移动次数(即最小 `numMoves` ) 。

示例 1:

输入: target = 2 输出: 3 解释: 第一次移动，从 0 到 1 。 第二次移动，从 1 到 -1 。 第三次移动，从 -1 到 2 。

示例 2:

输入: target = 3 输出: 2 解释: 第一次移动，从 0 到 1 。 第二次移动，从 1 到 3 。

提示:

  • `-109 9`
  • `target != 0`
参考解法

参考解法如下：

python
class Solution:
    def reachNumber(self, target: int) -> int:
        """
        LeetCode 754. Reach a Number

        核心结论：
        设前 k 步全部向右走，总和为 s = 1 + 2 + ... + k。
        如果 s >= abs(target)，且 s - abs(target) 是偶数，
        那么可以通过把若干步从“向右”改成“向左”，恰好到达 target。
        """
        target = abs(target)

        step = 0
        total = 0

        while total < target or (total - target) % 2 != 0:
            step += 1
            total += step

        return step


if __name__ == "__main__":
    solution = Solution()

    # 示例测试
    print(solution.reachNumber(2))  # 3
    print(solution.reachNumber(3))  # 2

    # 边界与补充测试
    print(solution.reachNumber(-2))  # 3
    print(solution.reachNumber(1))   # 1
    print(solution.reachNumber(4))   # 3
解练习分析

这道练习的关键是把“每一步向左或向右”转化为“先全部向正方向走，再翻转部分步数”的数学任务。

因为数轴左右对称，所以 `target` 为负数和正数本质相同，先令 `target = abs(target)`。

假设走了 `k` 步，并且每一步都向右走，那么最终位置是：

`sum = 1 + 2 + ... + k = k * (k + 1) / 2`

如果 `sum < target`，显然不可能到达目标，因为即使全部向右走也不够远。

当 `sum >= target` 时，考虑是否可以通过把某些步从向右改成向左来修正位置。假设被翻转的步数集合之和为 `x`，那么原来这些步贡献 `+x`，翻转后贡献 `-x`，总位置会减少 `2x`。因此最终位置为：

`sum - 2x = target`

移项得到：

`sum - target = 2x`

所以只要 `sum - target` 是偶数，就一定可以选择若干个步长凑出 `x`，从而到达目标。由于步长是从 `1` 到 `k` 的连续整数，能够凑出 `0` 到 `sum` 之间的任意整数，因此该条件充分且必要。

方法流程： 1. 将 `target` 取绝对值。 2. 从第 `1` 步开始累加步数和 `total`。 3. 当 `total < target` 或者 `(total - target)` 为奇数时，继续增加一步。 4. 第一次满足 `total >= target` 且差值为偶数时，当前步数就是最小答案。

复杂度分析： - 时间复杂度：`O(sqrt(target))`。因为前 `k` 步和约为 `k^2 / 2`，所以 `k` 约为 `sqrt(2 * target)`。 - 空间复杂度：`O(1)`。

边界条件： - `target` 为负数：必须先取绝对值，否则奇偶判断方向会混乱。 - `target = 1`：答案是 `1`。 - 非常大的 `target`，例如 `10^9`：循环次数约为 `44721`，完全可接受。 - `target != 0`，但如果扩展到 `target = 0`，答案应为 `0`。

常见错误： 1. 忽略负数目标，没有使用 `abs(target)`。 2. 只找到第一个 `total >= target` 就返回，忘记检查奇偶性。 3. 误以为 `sum - target` 为偶数只是必要条件，不知道它在连续步长 `1..k` 下也是充分条件。 4. 使用 BFS 或动态规划模拟位置，会导致状态空间过大，不适合 `10^9` 级别输入。 5. 判断条件写反，应该是继续循环直到同时满足 `total >= target` 且 `(total - target) % 2 == 0`。

考察中高质量答案应覆盖： - 数轴对称性，为什么可以取绝对值。 - 总步长三角数 `1 + 2 + ... + k`。 - 翻转某些步会让总位置减少两倍的步长和。 - 为什么只需要检查 `(total - target) % 2 == 0`。 - 为什么首次满足条件就是最小步数。

可追问点： - 能否用二分或公式先找到最小的 `k` 使得 `k(k+1)/2 >= target`？ - 如果每一步的步长不是 `1..k` 连续整数，奇偶条件还充分吗？ - 如果要求输出具体移动方案，而不是最少步数，应该如何构造？
