任务 第一则

信息粒缓存编排

▶ YouTube ▶ B站↗ 原始论文
任务 94/100

你负责一个企业级长上下文 RAG 服务：每次请求会检索到 20~200 个文档片段，每个片段 200~2000 tokens，LLM 支持复用已计算的 KV cache。线上发现很多请求的检索结果在语义上高度重复，但文本顺序、裁剪边界、模板包装不同，导致 prefix cache 命中率低；同时缓存显存只有 80GB，P99 首 token 延迟要求 < 800ms，答案准确率不能因为复用错误下降超过 0.5%。请设计一个“信息粒级别”的 KV 复用与调度方案：如何切分、判重、选择复用哪些粒度、如何在显存预算下淘汰，以及如何保证在线/离线一致性与正确性。

参考回答

我会先把任务建模为“带收益和风险约束的有向片段缓存选择任务”，核心不是简单按文本前缀缓存，而是把检索上下文拆成可独立验证的信息粒，并为每个信息粒维护规范化表示、语义指纹、token 边界、KV 版本和质量置信度。

第一步是信息粒构建。离线或检索后处理阶段，将文档片段按段落、表格行、标练习层级、引用块、代码块等结构切分；没有结构时用滑窗加语义断点。每个粒度记录原文 token span、归一化文本、embedding、SimHash/MinHash 指纹、来源文档版本、权限标签和模板无关内容。切分不能太细，否则注意力上下文依赖强、KV 管理开销大；也不能太粗，否则复用率低。我会把粒度控制在 128~512 tokens，并保留相邻粒的可合并能力。

第二步是判重与候选匹配。对于新请求的检索上下文，先做规范化：去模板、去时间戳噪声、统一引用格式，再通过语义哈希召回候选缓存粒；然后用 embedding 相似度、token overlap、来源版本、权限、时间有效性做多级过滤。只有满足强一致条件的粒才允许直接 KV 复用；语义相似但非字面等价的粒不能直接复用 KV，因为 KV 是对具体 token 序列的函数。对这类粒可以复用检索排序结果或摘要，但不能复用底层 KV，除非系统采用 canonical rewrite，把等价内容重写成缓存中的规范文本并把该文本真实拼入 prompt。

第三步是解决“非连续前缀”的编排。标准 Transformer KV cache 依赖 token 位置和前文，因此不能任意把多个粒的 KV 拼接后当作原始 prompt。可行方案有两个：一是构造 canonical prompt，把命中的信息粒按全局确定顺序拼接，形成 prefix DAG，每个节点是一个规范粒，边表示拼接顺序；只有当请求 prompt 的前缀路径与缓存 DAG 中路径完全一致时，才能复用该路径 KV。二是如果模型支持 paged attention、block-wise position 或文档块独立编码，则可以把粒作为独立 context block 复用，再在解码时组合注意力页。若模型不支持独立块编码，我会保守采用第一种，牺牲部分命中率换正确性。

第四步是在显存预算下选择缓存。对每个缓存粒或路径计算价值： value = 预期命中频率 × 节省计算量 × 延迟收益 × 准确率安全系数 / 显存占用。 显存占用近似为 layers × 2 × hidden_dim × token数 × dtype_bytes。淘汰策略不是单纯 LRU，而是 TinyLFU/LRU-K 加收益模型：高频短粒、长路径公共前缀、热门租户常用知识优先保留；低频、版本即将过期、权限范围窄、过长且不可共享的粒优先淘汰。若要更形式化，可以把缓存选择建成 0/1 knapsack；线上用贪心近似，按 value/size 排序并加分层配额，避免大客户或热点话练习挤占全部显存。

第五步是请求内调度。一次请求拿到候选粒后，先构造规范化上下文序列，再在 prefix DAG 中找最长可复用路径；如果有多个候选路径，则选择预计首 token 延迟最低且风险最低的路径。未命中的后缀现场 prefill，并把新路径异步写入缓存。写入需要 admission control：只有满足频率预测、长度阈值、版本稳定、权限可共享的粒才进入显存缓存；其他可以进入 CPU/NVMe 二级缓存或只保留元数据。

复杂度上，设请求包含 n 个信息粒，缓存索引规模为 M。语义哈希召回近似 O(n)，embedding ANN 查询为 O(n log M) 或亚线性；DAG 最长前缀匹配为 O(total_tokens 或 n)；缓存选择在线部分主要是 O(k log k)，k 为候选缓存项数。真正的大头是未命中 prefill，目标是用缓存把重复上下文的 prefill FLOPs 从 O(L) 降到 O(L_miss)。

正确性和一致性方面，我会设置几个硬约束：模型版本、tokenizer 版本、position encoding 配置、系统 prompt 模板版本、LoRA/adapter 版本、文档版本和权限标签必须一致；否则 KV 不可复用。所有缓存 key 中必须包含这些版本号。离线评估要做 A/B：比较 no-cache 与 cache 的答案一致性、引用准确率、幻觉率、P50/P95/P99 延迟、显存命中率。线上先 shadow，再小流量灰度，并对低置信复用设置 fallback：一旦发现引用冲突、文档版本过期或生成质量异常，退回重新 prefill。工程上还要处理租户隔离、隐私擦除、热更新失效、跨 GPU cache 路由和 cache stampede。

回答分析

强回答应该先指出“语义相似不等于 KV 可复用”这个关键边界，因为 KV cache 严格依赖 token 序列、位置编码、模型权重和前缀顺序。其次要把任务拆成切分、索引召回、合法性校验、缓存选择、在线调度、淘汰、评估监控几部分，而不是只说用 embedding 做相似度。优秀候选人会讨论 prefix DAG、canonical prompt、版本化 cache key、权限隔离、显存收益模型和 P99 延迟目标，并能给出近似复杂度与工程 fallback。常见错误包括：把语义相似文本直接复用 KV；忽略 position id 和系统 prompt 变化；只用 LRU 不考虑 token 长度和计算收益；只优化平均延迟不看 P99；没有考虑文档更新、租户权限和缓存污染。出练习者可以继续追问模型结构是否支持 block-level KV 拼接、如何评估 0.5% 准确率损失、以及多 GPU 环境下缓存路由和迁移成本。

编程练习 第二则

表示一个折线图的最少线段数

▶ YouTube ▶ B站↗ LeetCode
任务 95/100

给你一个二维整数数组 `stockPrices` ，其中 `stockPrices[i] = [dayi, pricei]` 表示股票在 `dayi` 的价格为 `pricei` 。折线图 是一个二维平面上的若干个点组成的图，横坐标表示日期，纵坐标表示价格，折线图由相邻的点连接而成。比方说下图是一个例子：

请你返回要表示一个折线图所需要的 最少线段数 。

示例 1：

输入：stockPrices = [[1,7],[2,6],[3,5],[4,4],[5,4],[6,3],[7,2],[8,1]] 输出：3 解释： 上图为输入对应的图，横坐标表示日期，纵坐标表示价格。 以下 3 个线段可以表示折线图： - 线段 1 （红色）从 (1,7) 到 (4,4) ，经过 (1,7) ，(2,6) ，(3,5) 和 (4,4) 。 - 线段 2 （蓝色）从 (4,4) 到 (5,4) 。 - 线段 3 （绿色）从 (5,4) 到 (8,1) ，经过 (5,4) ，(6,3) ，(7,2) 和 (8,1) 。 可以证明，无法用少于 3 条线段表示这个折线图。

示例 2：

输入：stockPrices = [[3,4],[1,2],[7,8],[2,3]] 输出：1 解释： 如上图所示，折线图可以用一条线段表示。

提示：

  • `1 5`
  • `stockPrices[i].length == 2`
  • `1 i, pricei 9`
  • 所有 `dayi` 互不相同 。
参考解法

参考解法：

python
from typing import List


class Solution:
    def minimumLines(self, stockPrices: List[List[int]]) -> int:
        n = len(stockPrices)
        if n <= 1:
            return 0

        # 折线图按日期从小到大连接相邻点
        stockPrices.sort(key=lambda x: x[0])

        # 至少有两个点时，至少需要一条线段
        ans = 1

        for i in range(2, n):
            x1, y1 = stockPrices[i - 2]
            x2, y2 = stockPrices[i - 1]
            x3, y3 = stockPrices[i]

            # 判断相邻两段斜率是否相同：
            # (y2 - y1) / (x2 - x1) == (y3 - y2) / (x3 - x2)
            # 为避免浮点误差，使用交叉相乘。
            dy1 = y2 - y1
            dx1 = x2 - x1
            dy2 = y3 - y2
            dx2 = x3 - x2

            if dy1 * dx2 != dy2 * dx1:
                ans += 1

        return ans
解练习分析

核心思想是：折线图必须按照日期从小到大连接点，因此第一步需要按 `day` 排序。排序后，连续若干个点如果共线，就可以用同一条线段表示；一旦相邻两段的斜率发生变化，就必须新增一条线段。

对于三个连续点 `(x1, y1)、(x2, y2)、(x3, y3)`，如果：

`(y2 - y1) / (x2 - x1) == (y3 - y2) / (x3 - x2)`

则说明这三个点在同一条直线上，当前线段可以继续延伸；否则说明在中间点处发生转折，需要增加一条线段。

为了避免浮点数精度任务，不应直接计算斜率除法，而应该使用交叉相乘：

`(y2 - y1) * (x3 - x2) == (y3 - y2) * (x2 - x1)`

由于所有 `dayi` 互不相同，排序后相邻点的 `dx` 一定不为 0，不存在竖直线除零任务。

边界条件： - 如果只有 1 个点，不需要任何线段，返回 `0`。 - 如果有 2 个点，一定需要 1 条线段，返回 `1`。 - 多个点全部共线时，答案为 `1`。 - 价格可能相同，水平线段斜率为 0，应正常处理。 - 日期输入无序，必须排序。

复杂度： - 时间复杂度：`O(n log n)`，主要来自排序；遍历统计为 `O(n)`。 - 空间复杂度：`O(1)` 或 `O(log n)`，取决于排序实现的额外空间；Python 排序通常可认为使用额外空间。

常见错误： 1. 忘记按日期排序，直接按照输入顺序判断，导致结果错误。 2. 使用浮点数比较斜率，可能因为精度误差导致误判。 3. 将相同斜率但不连续的线段合并，实际上只能合并排序后连续且共线的点。 4. 对 `n == 1` 返回 `1`，但一个点不构成线段，应返回 `0`。 5. 用约分后的斜率表示时没有正确处理正负号和零，容易出错；交叉相乘更简洁稳妥。

出练习者可能会追问： - 为什么不能用浮点数比较斜率？ - 为什么只需要比较相邻两段斜率？ - 如果 `day` 可能重复，会发生什么？如何处理竖直线？ - 时间复杂度的瓶颈在哪里，能否优化？ - Python 中整数乘法是否会溢出？如果是 Java/C++ 呢？

高质量答案应覆盖：排序的必要性、共线判断、交叉相乘避免精度任务、边界条件和复杂度分析。
